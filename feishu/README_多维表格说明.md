## 一、权限已经是对的，不用改

我核过 `link_share_entity`，当前值是 **`anyone_readable`**——拿到链接的人都能打开阅读。

之前有一轮我说"链接打不开、老师会被要求登录"，那是错的：当时用命令行探测时没带访客 cookie，被弹到了登录页，**不代表真的无权访问**。用浏览器无痕打开是能看的。

### 1. 开发日志：把"无"换成了真问题

你原来三条日志的「遇到的问题」写的是"无"，「解决方案」是"逐项修复并提交"。这两格是老师最想看的部分，写"无"等于告诉对方今天没遇到任何困难——不可能，也不可信。

我按仓库里的实际修复记录补写了，例如：

- 10-28：单帧丢包会把「有人」误判成「无人」；按键消解后冷却到期没回初始态，之后真出事会永久沉默

### 开发日志：一条命令（已停用）

```bash
# 已停用，勿运行
cd guardian
python tools/feishu_sync.py
```

它会：

1. 从 `git log` 按天聚合提交
2. 已有当天记录就**覆盖**，没有就**新建**（跑十次也不会重复）
3. 自动填好：今日工作内容、日期、变更文件数、变更行数、对应提交链接

**它填不了「问题 / 方案 / 计划」**——git 里没有这层信息。这三格要么写进 `tools/feishu_sync.py` 的 `NOTES` 字典，要么直接在飞书网页里填。

脚本末尾会提示哪几天缺这三格，不会静默留空。

### 任务看板 / 里程碑 / 指标

这三张表手动维护即可。真正需要动的只有：

- 任务看板的 `状态` 和 `完成度`
- 指标验证的 `实测值`（硬件到货、数据采完才填）

## 五、为什么用 lark-cli 而不是开放平台 API

> 同步已于 2026-11-09 停用，本节只解释当时的技术选择，不代表现在还要跑。

上一轮我的方案是"导出 CSV → 你手动导入"，那其实是不必要的麻烦。后来改成直接写表。

实现方式用的是 `lark-cli`（WorkBuddy 的飞书连接器带的命令行），它走**当前登录用户的身份**：

- 不用建企业自建应用
- 不用配 `app_secret`
- 不用把应用加成表协作者（这一步是最容易 403 的地方）

代价是：跑脚本的这台机器必须已经登录过飞书。换机器要重新连一次。
