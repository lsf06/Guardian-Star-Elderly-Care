> 这份文件不复述建议，只给**对着代码核过的结论**。

## 结论先看

- 6 条"严重漏洞"里：**1 条是真缺口**（离线/送达闭环），**2 条方向对但改法会增加误报**，**3 条讲的是另一份方案**（距离门 5–8、底噪 10 / 呼吸 50 / 阈值 30、外壳前倾 10°）——本仓库没有这些参数。

## 二、为什么"改门磁"这条不能照着做

对方建议：门开 10 秒只进"疑似离家"，继续监测，别关掉安全判定。

问题在于：**"门开着 + 雷达看不见人"在信号上无法区分下面两件事。**

| 真实情况 | 雷达 | 门磁 | 设备能区分吗 |
|---|---|---|---|
| 老人真的出门了，门没关严 | 看不见 | 开 | 不能 |
| 老人倒在门外楼道，雷达照不到 | 看不见 | 开 | 不能 |
| 老人开门通风，坐在沙发上看电视 | **看得见** | 开 | 能 → 当前代码走 `HOME`，不受影响 |

如果按建议把"门开 + 看不见人"也留在监测态，后果是：老人正常出门后，设备会对着空房间问候、升级、推送给家属——**每天几十次误报**，直接违反"别让老人烦到拔电源"这条唯一的产品原则。

所以现在的写法是对的：**门开 + 看不见人 = 离家**（`:190-197`），这是承认"我判断不了"，而不是"我判断错了"。
它的代价必须写进边界：**门长时间不关、人又离开视场时，设备不监护。**

> 如果要进一步降低这个代价，方向不是改状态机，而是加一条**逃生口**：
> 离家持续超过 N 小时且门一直没关 → 推一条"设备判定离家，无法监护"给家属。
> 这是新增行为，需要配套测试，列为 **P1**，不在本轮做。

## 三、真缺口：离线与送达闭环（P0）

对方这条说对了，而且它比门磁重要得多：**"按了红键"不等于"家属收到了"。**

现状（改之前）：

```python
with urllib.request.urlopen(req, timeout=10) as r:
    return r.status == 200        # 只看 HTTP，不看 PushPlus 的业务码
```

三个问题叠加：HTTP 200 但业务码失败（token 过期、当日限额）也当成功；网络抖动一次就放弃；失败只 `print`，事后无从追查。

本轮已修（只动 `voice.py`，不碰状态机）：

1. **校验业务码**：解析返回 JSON，`code != 200` 视为失败；
2. **三次退避重试**（1 s / 2 s），仅对异常与非 2xx 重试；
3. **失败落盘**：写入 `data/_push_failed.jsonl`（时间、内容、原因），供人工补发与事后取证。

仍然做不到、需要家属端或服务端的（**写在这里，不假装有了**）：

- 心跳与"最后一次成功送达时间"；
- 断电/断网期间的离线检测（设备自己发不出消息）；
- 网络恢复后自动补发队列；
- 老人按了红键之后的**送达确认**（PushPlus 只给"已受理"，不给"已读"）。

## 四、实验设计（P1）

`breathhold` 这个标签保留（改名会破坏已有 CSV 的 `label` 列与 `sweep.py` 的分组），但**表述必须改**：

- 它测的是"**人还在原地、呼吸微动消失时，雷达会不会丢目标**"，不是"测呼吸停止"，更不能写成"验证呼吸监测"；
- 只在本人身上做，20 秒以内，不安排老人参与；
- 结论只能写成"该雷达在此摆放下的微动检出边界"，不能外推成"能发现呼吸异常"。
