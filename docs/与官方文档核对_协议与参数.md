## 一、代码 bug：工程模式门能量错位 2 字节

### 官方原文（协议 V1.09 §2.3，第 20–21 页）

工程模式上报帧的 payload 是 **35 字节（0x23）**，顺序为：

```
[0]    数据类型 0x01
[1]    头部 0xAA
[2]    目标状态
[3-4]  运动目标距离
[5]    运动目标能量
[6-7]  静止目标距离
[8]    静止目标能量
[9-10] 探测距离
[11]   最大运动距离门
[12]   最大静止距离门
[13-21] 运动距离门 0..8 能量   ← 9 字节
[22-30] 静止距离门 0..8 能量   ← 9 字节
[31]   光敏检测值
[32]   OUT 脚输出状态
[33]   0x55
[34]   0x00
```

官方给的示例帧：

```
F4F3F2F1 2300
01AA031E003C00003900000808
3C2205030304030605
000039101306060804
6001 5500 F8F7F6F5
```

### 我原来的写法

```python
static_start = len(payload) - 2 - MAX_GATES   # 从帧尾反推
motion_start = static_start - MAX_GATES
```

**错在哪**：从帧尾往前推时，只扣了 `0x55 0x00` 两字节，
**漏掉「光敏 + OUT」这两字节**。于是两组门能量整体前移 2 字节。

### 实测后果

```
代码解出运动门: [5, 3, 3, 4, 3, 6, 5, 0, 0]
官方原文运动门: [60, 34, 5, 3, 3, 4, 3, 6, 5]
```

**整段数据全错。** 而且错得"看起来合理"——都是 0–100 之间的数字，
不报错、不越界，只是把「光敏 96」和「OUT 1」当成了第 8、9 个门的能量。

### 这个 bug 为什么一直没被发现

原来的自检用**自己构造的帧**验证自己写的解析：

```python
RAW_ENG = bytes([...] + ENG_MOTION + ENG_STATIC + [7, 1] + [...])
```

打包时按"错误的理解"写帧，解析时按"同一个错误的理解"读，
**两边错在同一处，所以一直 PASS。**

> 这条写进 `src/selftest.py` 的头注释里了：
> 「不要用『自己打包 → 自己解析』来验证协议。那样只能证明代码自洽，偏移错了照样通过。」

### 修法

改成**从帧头往后定位**，不依赖帧尾：

```python
motion_start = 13      # payload[11]=最大运动门, [12]=最大静止门
static_start = motion_start + MAX_GATES
light = payload[static_start + MAX_GATES]
out   = payload[static_start + MAX_GATES + 1]
```

### 验证

把官方两帧原文硬编码进 `selftest.py` 作为基准：

```
PASS  9 个运动门能量逐字节一致
PASS  9 个静止门能量逐字节一致
PASS  光敏 = 96
PASS  OUT = 1 (有人)
```

**并且做了反向验证**：故意把错误逻辑放回去，4 项立刻 FAIL；恢复后 PASS。
这说明测试真的能抓住这个 bug，不是摆设。

## 二、事实错误：G0/G1 并没有被出厂关闭

### 我写过的

> 「G0（0–0.75 m）与 G1（0.75–1.5 m）的静止门限出厂为 0，即关闭。
> 所以静止检测实际从 1.5 m 起。」

### 官方原文（协议 V1.09 §2.2.4「读取参数」ACK 示例）

```
雷达ACK：(成功，最大距离门 8，配置运动距离门 8，静止距离门 8，
0~8运动灵敏度 20，0~8静止灵敏度 25，无人持续时间 5 秒)

FD FC FB FA 1C 00 61 01 00 00 AA 08 08 08
14 14 14 14 14 14 14 14 14     ← 运动灵敏度 G0..G8 = 20
19 19 19 19 19 19 19 19 19     ← 静止灵敏度 G0..G8 = 25
05 00                          ← 无人持续 5 秒
```

逐字节解出来：

| 位置 | 值 | 含义 |
|---|---|---|
| p[17] | **25** | G0 静止灵敏度 |
| p[18] | **25** | G1 静止灵敏度 |
| p[19..25] | 25 | G2..G8 静止灵敏度 |

**九个门全部有灵敏度值，没有任何一个被关闭。**

而且说明书 §5.2 明确说了「设为 100 才是关闭」：

> 「如果将某个距离门的灵敏度设置为 **100** 时，可达到不识别此距离门下目标的效果。」

**关闭 = 100，不是 0。** 我把 0 当成了关闭，还倒推出一个不存在的门槛。

### 影响

这条错误被复制到了 **4 个文件**里：`docs/项目说明书.md`、`docs/边界与指标.md`、
`hardware/BOM.md`、`hardware/wiring.svg`（接线图的脚注）、`README.md`。

现在全部改掉了。

## 三、方向读反：「1.5 m」是上限不是下限

### 官方原文（说明书 §5.2）

> 「以距离门为单位进行设置，每个距离门为 0.75 m。
> 例如设置最远距离门为 2，则只有在 **1.5 m 内**有人体存在才会有效探测到并输出结果。」

注意这句的前提是「**最远**距离门设为 2」。所以 1.5 m 是**上限**（覆盖到 1.5 m 为止），
不是「从 1.5 m 开始」。

### 说明书表 2（第 19 页）的官方参数

| 项 | 值 |
|---|---|
| **探测距离** | **0.75 m ～ 6 m，可调** |
| 距离分辨率 | 0.75 m |
| 探测角度 | ±60° |
| 扫频带宽 | 250 MHz |
| 供电 | DC 5V，>200mA |
| 平均工作电流 | 79 mA |
| 频段 | 24–24.25 GHz |

**物理下限是 0.75 m。**

### 改成了什么

不再说「物理限制 ≥1.5 m」，改成：

> **推荐 2–3 m 摆放，官方物理下限 0.75 m。**
> 近距不推荐是**工程理由**（不是物理限制）：
> 1. 0.75 m 内只有 G0 单门，分辨率 0.75 m，区分度最低；
> 2. 近场反射抬高静止能量，坐着的人和空椅子分不开；
> 3. 放 0.8 m 会正对老人后背或侧身，波束与胸腔起伏接近垂直，微动最难测。
>
> 真要在近距用，必须实测：坐在目标位置 60 秒，看 G0/G1 静止能量是否稳定高于空场基线。

**区别很重要**：「物理上做不到」和「工程上不推荐」是两回事。
前者不能改，后者可以测过之后再改。答辩时这么说才不会被打。

### 一处遗漏（不影响判定，但值得知道）

官方表 14 里目标状态其实有 **7 个值**，不是 4 个：

| 值 | 含义 |
|---|---|
| 0x00 | 无目标 |
| 0x01 | 运动目标 |
| 0x02 | 静止目标 |
| 0x03 | 运动 & 静止目标 |
| **0x04** | **正在底噪检测中**（仅底噪检测时有效） |
| **0x05** | **底噪检测成功**（仅底噪检测时有效） |
| **0x06** | **底噪检测失败**（仅底噪检测时有效） |

0x04–0x06 只在执行「底噪检测」命令时才出现，本项目没用到这个命令，
所以 0x04–0x06 不会实际出现。`STATE_NAMES` 只映射了 0–3，**够用但要知道为什么不完整**。
